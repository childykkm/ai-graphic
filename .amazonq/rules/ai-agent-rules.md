# ai-agent-rules.md — 공통 AI 에이전트 행동 강령

> 이 파일은 모든 프로젝트에서 공통으로 적용되는 AI 에이전트 행동 규칙입니다.
> 프로젝트별 project-rule.md에서 이 파일을 참조하며, 프로젝트 고유 규칙은 project-rule.md에 정의합니다.
> AI 에이전트는 작업 시작 전 이 문서를 최우선으로 파악하십시오.

---

## 0. 기본 원칙

모든 분석, 코드 생성, 터미널 명령 수행 전에 이 문서를 최우선 순위로 파악하십시오.

---

## 1. 언어 및 커뮤니케이션

- 모든 답변, 설명, 코드 주석은 **한국어**로 작성한다.
- 기술 용어(함수명, 변수명, 라이브러리명 등)는 원문 그대로 사용한다.
- 불명확한 요구사항은 작업 전에 반드시 확인 질문을 한다.

---

## 2. 구조 분석 의무

- 명령 수행 전 프로젝트 전체 구조를 상세히 파악한다.
- 패키지/모듈 간 의존성과 역할을 문맥에 반영하여 코드를 배치한다.
- 기존 코드 패턴과 컨벤션을 파악하고 일관성을 유지한다.

---

## 3. 권한 및 실행

- 에이전트에게는 터미널 실행 및 파일 생성/수정 권한이 부여된다.
- 필요 시 주도적으로 파일을 구성하되, 파괴적 변경(삭제, 대규모 리팩토링) 전에는 반드시 확인한다.
- 터미널 명령 실행 전 의도와 영향 범위를 먼저 설명한다.

---

## 4. 설계 우선순위

### 4.1 DRY (Don't Repeat Yourself)
- 중복 코드를 철저히 피한다.
- 유사 로직 발견 시 기존 코드를 리팩토링하여 통합한다.
- 범용 로직은 공통 레이어(core, utils 등)로 분리하여 재사용한다.

### 4.2 관심사 분리 (Separation of Concerns)
- 아키텍처 용도에 맞는 폴더/레이어에 코드를 배치한다.
- UI 컴포넌트에 비즈니스 로직을 직접 작성하지 않는다.
- 데이터 접근(API 호출)은 서비스 레이어를 통해서만 수행한다.

### 4.3 모노레포 준수 (해당 프로젝트에 적용 시)
- 패키지 간 의존성 방향을 준수한다: `ui` → `core`, `core` → 외부 라이브러리
- 패키지 경계를 넘는 직접 파일 참조를 금지한다. Path Alias를 사용한다.

---

## 5. 코딩 스타일

| 대상 | 규칙 |
|------|------|
| 컴포넌트, 클래스, 타입, 인터페이스 | PascalCase |
| 변수, 함수, 훅, 메서드 | camelCase |
| 상수 | UPPER_SNAKE_CASE |
| 파일명 (컴포넌트) | PascalCase.tsx |
| 파일명 (유틸/서비스/훅) | camelCase.ts |

- 문자열 하드코딩 금지 — 상수 파일로 분리하여 관리한다.
- `any` 타입 사용은 서버 응답 파싱 등 불가피한 경우에만 허용하며, 주석으로 이유를 명시한다.
- 함수는 단일 책임 원칙을 따른다. 하나의 함수가 하나의 역할만 수행하도록 한다.

## 6. 코드 품질 기준

- `console.log`는 커밋 전 반드시 제거한다. 디버그 출력은 `console.warn` 또는 `console.error`를 사용한다.
- PR/커밋 전 lint 검사를 통과해야 한다.
- **TypeScript 에러는 커밋 및 빌드 전 반드시 수정한다.** 타입 에러를 `as any` 또는 `// @ts-ignore`로 우회하는 것을 금지한다. 불가피한 경우 `// @ts-expect-error`와 함께 이유를 주석으로 명시한다.
- 에러 처리를 생략하지 않는다. API 호출, 파일 파싱 등 실패 가능한 모든 작업에 에러 핸들링을 포함한다.
- 민감 정보(토큰, 비밀번호, API 키 등)를 코드에 하드코딩하지 않는다. 환경변수를 사용한다.
- `.env` 파일은 절대 커밋하지 않는다.

### 6.1 API 응답 데이터 처리 — 옵셔널 체이닝 적용 기준

API로부터 받은 데이터를 적용할 때 아래 기준에 따라 옵셔널 체이닝(`?.`)과 Nullish 병합(`??`)을 사용한다.

**옵셔널 체이닝을 적용해야 하는 경우**
- 서버 응답 구조가 항상 보장되지 않는 중첩 필드에 접근할 때
  ```ts
  // ✅
  const name = res?.user?.profile?.name;
  const items = res?.data?.items ?? [];
  ```
- 배열 여부가 불확실한 응답을 순회하기 전
  ```ts
  // ✅
  const list = Array.isArray(res?.data) ? res.data : [];
  ```
- 선택적(optional) 필드로 정의된 타입의 프로퍼티에 접근할 때
  ```ts
  // ✅ brand_id?: number | string
  const id = item.brand_id ?? brand?.id;
  ```

**옵셔널 체이닝을 남용하지 않아야 하는 경우**
- 타입 상 `non-nullable`이 보장된 필드 (불필요한 `?.`는 타입 정확도를 낮춘다)
  ```ts
  // ❌ id는 항상 존재하는 필드
  const id = user?.id;
  // ✅
  const id = user.id;
  ```
- 이미 null/undefined 체크가 완료된 스코프 내부
  ```ts
  // ✅ if 블록 안에서는 불필요한 ?. 생략
  if (res && res.data) {
    const name = res.data.name; // res.data?.name 불필요
  }
  ```

**Nullish 병합(`??`) 기본값 처리 원칙**
- 빈 문자열(`''`)과 `0`을 유효한 값으로 취급해야 할 때는 `||` 대신 `??`를 사용한다.
  ```ts
  // ✅ qty가 0일 때도 유지됨
  const qty = item.order_qty ?? 0;
  // ❌ qty가 0이면 1로 덮어씌워짐
  const qty = item.order_qty || 0;
  ```
